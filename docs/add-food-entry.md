# Add food entry

`GET /meals/new` shows the team's styled Add form. `POST /meals/new`
validates and saves one document to
`food_entries` in the database named by `MONGO_DBNAME`. This reuses the team's
existing Flask app and MongoDB connection. `/add` remains a GET/POST alias.
Run `python app.py` to use the integrated UI and real Add handler on port 5000.
The separate `frontend_app.py` on port 5001 remains a frontend-only preview.

## Proposed shared document contract

These names match the current Add form. They are an integration proposal;
the team's setup code defines the collection but does not establish stored
field names or types. The newer UI's sample view models use `name`, `loggedAt`,
and `id`; those are not MongoDB documents. Confirm the mapping with the
homepage, history, edit, delete, and search feature owners before merging.

| Field | Stored type | Meaning |
| --- | --- | --- |
| `_id` | MongoDB ObjectId | Generated by MongoDB; use it to identify records for edit/delete. |
| `date` | String | A real calendar date in canonical `YYYY-MM-DD` form. |
| `food_name` | String | Nonempty food name with outer whitespace removed. |
| `meal` | String | Exactly `breakfast`, `lunch`, `dinner`, or `snacks`. |
| `calories` | Number (double) | Finite value >= 0, in kcal for this entry. |
| `protein` | Number (double) | Finite value >= 0, in grams for this entry. |
| `carbs` | Number (double) | Finite value >= 0, in grams for this entry. |
| `fat` | Number (double) | Finite value >= 0, in grams for this entry. |

Extra submitted fields, including a client-provided `_id`, are ignored. Dates
can be historical or future dates; the requirements do not prohibit either.
Nutrition values describe the logged entry, not an assumed 100 g portion.

## Behavior

- All seven fields are required and checked on the server as well as by the browser.
- Invalid input returns HTTP 400, displays errors, and retains displayable inputs.
- Database errors return HTTP 503 with retained inputs and no success message.
- A successful insert redirects with HTTP 303 to `GET /meals/new?saved=1`.
  Refreshing this GET does not insert another record. This does not prevent
  two separate POST requests from creating two records.
- `saved=1` controls a simple success notice; it is not a database receipt.
- Database credentials are loaded from the ignored `.env`; database error
  details are not rendered in the page.
- The Add page extends the team's `base.html` and uses its CSS, navigation,
  and local assets. Its real-data mode disables the frontend preview guard.
  Small page-specific styles support its new date/category and nutrition fields.

## Homepage integration

The homepage owner can link to the form from a Jinja template with:

```html
<a href="{{ url_for('add_meal') }}">Add food</a>
```

The existing UI's Add button already targets this endpoint. Its Today, Meals,
Search, Edit, Delete, and Goals views retain their sample-data preview behavior;
only Add is connected to MongoDB in this feature. New entries will not appear
in sample lists or summaries until their owners connect database reads.

Daily summaries can read the numeric macro fields directly and filter `date`
using a `YYYY-MM-DD` string. When adapting stored records to the current UI,
map `food_name` to its display `name` and stringify `_id` for its `id`.
The stored `date` is a date only, not the UI fixture's `loggedAt` timestamp:
the team must decide whether to keep a date-only display or also collect time.
The Add form includes meal category and requires all macros, following the
original feature requirements; the original preview instead has a datetime
and optional macros. If the team chooses a different schema or requirements,
update the writer, readers, and tests together.

## Validation

Run `python -m unittest discover -s tests -v` for offline checks covering valid
entries, numeric conversion, zero and decimal values, all meals, real dates,
missing or malformed inputs, HTML escaping, unknown fields, database errors,
and refreshing after a successful save, plus both Add URLs and the team's UI
navigation. The tests do not establish Atlas access.

For an Atlas check, use a uniquely named development test entry. Save through
the form and confirm one matching document with the above types in
`food_entries`; refresh the success page and verify the count remains one.
Remove only that test document after checking. Do not delete teammates' records
or change database users, credentials, or network rules as part of this check.

The Add feature does not implement database reads for homepage summaries,
history, edit, delete, search, or goals. Their existing preview handlers are
reused without changing `frontend_app.py`.
